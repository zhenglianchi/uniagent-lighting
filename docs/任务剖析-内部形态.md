## 3.5 task 数据从哪来、怎么下发（数据源 + 双通道）

### 3.5.1 数据源：task.jsonl 什么时候生成、谁读

1. **离线生成**：`scripts/data/make_humanevalfix_data.py` 从 HumanEvalFix 数据集
   构建 `work/data/humanevalfix_train161.jsonl` / `humanevalfix_val.jsonl`
   （每条记录 = §2.1 的完整 JSON，含 prompt / tools_kwargs / reward_model）；
2. **训练启动时加载**：`trainer_base.py:545 _init_dataloader` →
   `create_rl_dataset(config.data.train_files, ...)`（读 jsonl，转 RL 数据集）→
   `StatefulDataLoader`（564 行）；
3. **每个 step 消费一条 batch**：`trainer_base.py:1131 _add_batch_to_generate`：
   `next(self.train_dataloader_it)` → batch_dict（含 raw_prompt / tools_kwargs /
   data_source / reward_model）。**sample 20 的 jsonl 记录就是在这里进入内存的**。

### 3.5.2 下发双通道（内部形态没有 task.json 文件）

`_add_batch_to_generate`（trainer_base.py:1131-1150）一次性做两件事：

```python
# 通道 A：把 prompt 注册进 TQ（tag-only，供 ReplayBuffer 状态机跟踪）
tags = [{"is_prompt": True, "status": "pending", "global_steps": self.global_steps}] * len(batch)
tq.kv_batch_put(keys=list(batch["uid"]), partition_id="train", tags=tags)

# 通道 B：整个 batch 以内存参数交给 agent 框架
self.agent_loop_manager.generate_sequences(batch)
```

| 通道 | 内容 | 流向 | 用途 |
|---|---|---|---|
| A | `uid` + tag（pending/running/finished/failure） | TQ | ReplayBuffer 判断该组是否完成、staleness 排序 |
| B | batch（raw_prompt / tools_kwargs / uid / global_steps） | `generate_sequences` → framework → `_run_session` → runner 函数参数 | **真正的 task 内容** |

**读取点**：runner 从函数参数拿 task——`mini_swe_agent_runner.py:570`
`extract_task(raw_prompt, tools_kwargs)` 解析出 `instance_id` / `fail_to_pass` /
`env.files`。所以内部形态**没有 task.json 文件**，task 内容全程在内存里流动。

### 6.5.2 核心数据结构（先记这些）

**`TrajectoryBuffer`（session.py:36）——一条轨迹的 token 级缓冲**：
```python
class TrajectoryBuffer:
    prompt_ids: list[int]          # 输入 token（首轮编码后固定）
    response_ids: list[int]        # 输出 token（每轮生成/工具结果增量 append）
    response_mask: list[int]       # 1=模型生成，0=工具结果（loss 只算 1）
    response_logprobs: list[float] # 生成 token 的 logprob（工具结果位置为 0.0）
    generation_versions: list      # [(min_global_steps, max_global_steps)] 每轮一次
    routed_experts: Any | None     # MoE 路由（本任务无）
```

**`ChainState`（session.py:79）——一条“链”**：`chain_id`、`message_history`、
`message_tip_hash`、`active_tool_schemas`、`buffer`（上面的 TrajectoryBuffer）、
`last_assistant_start`（回滚锚点）、`updated_seq`。

**`MaterializedChain`（session.py:94）**：物化后的链 = `trajectory` + `order_seq`。

**`EncodedData`（session.py:102）**：`_prepare_generation_inputs` 的产物——本轮
的 `buffer`（含增量）、`context_ids`、`sampling_params`、`messages`、`tools`、
`chain_id`、`capacity_exhausted`、`last_assistant_start` 等。

**`Trajectory`（gateway/session/types.py:45）**：最终物化结果——`prompt_ids /
response_ids / response_mask / response_logprobs / reward_info / num_turns /
extra_fields（min/max_global_steps、materialization_reason）`。

| 工具结果 mask=0 | session.py:447 | 工具输出不参与 loss |
| 模型 token mask=1 + logprob | session.py:272-297 | GRPO 需要的生成信号 |
| logprob 对齐校验 | session.py:639 | 防 logprobs 与 token 错位（配合 vLLM 修复） |
| 容量检查 / max_tokens 裁剪 | session.py:448-465 | 单条轨迹不超限 |
| 回滚截断 | session.py:414-435 | 重发纠正时去掉上一轮未提交生成 |
| 分链物化 | session.py:712 | 长会话冻结 + 开新链 |
| 版本 span | session.py:770 | min/max_global_steps 供 off-policy 判断 |
| 空响应跳过 | framework.py:883 | Mooncake 0 字节 slice 防护 |
| TQ 字段拼接 | framework.py:925 | prompts/responses/input_ids/loss_mask/rm_scores |
| 落盘 json/npz | framework.py:757 | 可读摘要 + token 级数组 |

### 6.5.14 一句话总结

**轨迹 = 每轮“模型生成（mask=1 + logprob）”与“工具结果（mask=0）”交替 append 进
链的 TrajectoryBuffer，finalize 时物化成 Trajectory，再经 framework 拼成
prompts/responses/input_ids/loss_mask 写进 TQ**——Gateway 是唯一的轨迹来源，
runner 全程不碰轨迹。

## 1. 端到端数据流（学习主线）

```
① Agent 决策循环                    ② Gateway 会话（uni-agent）

                                         └─ generate: 调 vLLM、append response
                                         └─ finalize: 物化链 → Trajectory 列表

③ 框架层（uni-agent）               ④ 数据平面（TransferQueue）
   framework.py                         TQ KV store
   └─ _trajectory_to_tq_field_and_tag ─▶  └─ kv_batch_put（prompts/responses/
   └─ _write_session_trajectories_to_tq     logprobs/masks/rm_scores/num_turns）

⑤ 训练（verl）                     ⑥ 权重 → 服务

```

## 2. Gateway 源码定位（重点）

所有路径基于仓库 `vendor/uni-agent/uni_agent/`。

### 2.1 会话与链（session.py）——轨迹的诞生地

| 函数 | 作用 |
|---|---|
`session.py::run_generation` | 每轮生成入口：prepare → 调模型 → commit 到链 |
`_prepare_generation_inputs` | 编码消息、选链、**容量检查**（`max_trajectory_length`） |
`_select_chain` | 通过消息 hash 匹配已有链（续链/回滚） |
`_commit_generation_to_chain` | 生成结果 append 到链的 buffer（response_ids/mask/logprobs） |
`_close_length_exhausted_chain` | 长度耗尽时物化链（→ 空轨迹的产生点） |
`finalize` | 会话结束：物化所有链 → 返回 Trajectory 列表 |

**关键数据结构**：`TrajectoryBuffer`（prompt_ids / response_ids / response_mask /
response_logprobs / generation_versions）——一条轨迹的 token 级内容全在这里。

### 2.2 轨迹转训练样本（framework.py）——轨迹如何变成 verl batch

| 函数 | 作用 |
|---|---|
`_trajectory_to_tq_field_and_tag` | Trajectory → TQ 字段（**重点**：字段如何组装） |

**产出的字段**（verl 训练直接消费）：

| 字段 | 含义 |
|---|---|
`prompts` / `responses` | 输入输出 token ids（tensor） |
`input_ids` / `attention_mask` / `position_ids` | 拼接后完整序列 |
`response_mask` / `loss_mask` | 哪些 token 参与 loss（工具结果 = 0） |
`rollout_log_probs` | 生成时 logprob（GRPO 需要） |
`rm_scores` | reward（最后一位置 reward_score） |
`num_turns` | 轮次（int64 tensor，8B 修复点） |
`global_steps` / `min/max_global_steps` | 权重版本跨度（off-policy 判定） |

`verl/workers/rollout/vllm_rollout/vllm_async_server.py` | rollout 引擎（EAGLE-3 投机、logprobs 修复） |

# uni-agent 源码导读

> 面向已完成训练侧（verl）学习、要深入 uni-agent 侧的读者。本文按
> `vendor/uni-agent/uni_agent/` 的目录逐块拆解，每块给出文件、关键类/函数与含义，
> 并在最后给出学习主线。配套「数据流与 Gateway 导读」见 `本文附录 A`。

## 0. 定位与整体架构

uni-agent 是 **agent 编排层**：把任意 agent harness 接入、Gateway 模型端点、
会话/链轨迹物化、沙箱执行、任务与工具抽象统一起来，产出 **verl 可直接消费的
TQ 数据**。它不启动训练（训练入口永远是 `verl.trainer.main_ppo`），而是通过
`agent_loop_manager_class=AgentFrameworkRolloutAdapter` 注入 verl 的 rollout 阶段。

```
verl trainer（训练/消费 TQ）
   ↑ TransferQueue（SimpleStorage / MooncakeStore）
uni-agent framework（写 TQ：_write_session_trajectories_to_tq）
   ↑ agent runner（mini_swe_agent_runner / claude_code_runner / external_agent_runner）
uni-agent gateway（模型端点 + session/链轨迹物化）
   ↑ OpenAI/Anthropic 兼容调用
agent（mini-swe-agent / Claude Code / 任意外部 agent） + sandbox（执行环境）
```

目录速览：

| 目录 | 职责 |
|---|---|
| `framework/` | 训练侧对接层：adapter、AgentFramework、runner 分发、写 TQ |
| `gateway/` | 模型端点 + 会话/链 + 轨迹物化 + OpenAI/Anthropic 协议适配 |
| `agents/` | 内置 agent（mini_swe_agent / react / claude_code）与抽象 |
| `sandbox/` | 沙箱抽象与实现（docker/local/modal/vefaas/...） |
| `tasks/` | 任务定义（swe_bench / swe_rebench）与 reward |
| `tools/` | 工具抽象（shell / edit_file / submit / finish） |
| `logging/` | 会话/轨迹日志（LogContext、脱敏） |
| `utils.py` | 通用工具 |

## 9. 关键横切概念

**Runner 契约**：`async def runner(*, raw_prompt, session, sample_index, tools_kwargs, run_timeout)`——
uni-agent 框架不关心你用什么 agent，只要满足这个签名，就能被 `ray_task` / `inline_async` 分发。

**轨迹生命周期**：

```
GatewaySession（链累积多轮）
  → finalize → Trajectory 列表（prompt/response/mask/logprobs + reward）
  → _write_session_trajectories_to_tq → TQ fields（prompts/responses/input_ids/loss_mask/global_steps）
  → trainer 经 ReplayBuffer 拉走
```

**我们的补丁位置**（对应模块）：`session.py`（固定端口、logprobs 对齐）、
`codec.py`（hermes JSON 修复重试）、`framework.py`（空响应轨迹跳过）、
`gateway/adapters`（协议容错）——详见 `docs/修改与补丁汇总.md`。

## 10. 建议学习主线

1. `framework/entry.py`（adapter 怎么起 Gateway + framework worker）→ 已学
2. `framework/framework.py` 的 `generate_sequences → _run_session → _write_session_trajectories_to_tq`（**核心数据流**）
3. `gateway/gateway.py` + `session/session.py`（模型端点 + 链机制，**轨迹诞生地**）
4. `gateway/session/codec.py`（消息编解码 + 工具调用解析）
5. `gateway/adapters/openai.py`（OpenAI 兼容入口，理解“任意 agent 接入”）
6. `uni_agent_ext/agents/mini_swe_agent_runner.py`（我们的 runner 怎么用 session 跑 agent）
7. 对照 `本文附录 A` 的端到端图收尾

> 一句话总结：**uni-agent = Gateway（端点+轨迹）+ framework（分发+写 TQ）+ runner
> 契约（任意 agent 接入）+ sandbox/tasks/tools（执行与任务抽象）**，训练侧只认
> “generate_sequences + 输出进 TQ”这个契约。
