# 修改与补丁汇总（Patch Registry）

> 记录本项目在 verl / uni_agent / TransferQueue / 训练脚本上的全部本地修改与
> 上游补丁：改动内容、原因、影响与验证状态。覆盖白盒（mini-swe-agent）、
> 黑盒（Claude Code）、双机全异步 + Mooncake 三个阶段。

## 一、verl 训练引擎层

### 1. EAGLE-3 投机解码 logprobs 空修复（vllm#30059）

- **文件**：`verl/workers/rollout/vllm_rollout/vllm_async_server.py`
- **改动**：请求 logprobs 时 `sampling_params["logprobs"] = 0 → 1`
- **原因**：vLLM 0.11.1 在 EAGLE-3 投机解码下 `logprobs=0` 返回空 logprobs
  （vllm#30059），verl 的 old_log_prob 全丢，GRPO 无法训练。
- **影响**：单机 spec run（25 步）前置修复；吞吐 +41.7% 无副作用。
- **记录**：verl commit `5fa045e`，补丁文件 `verl_vllm_logprobs_spec_fix.patch`

### 2. merge=True 时 LoRA 权重物化（verl#7014）

- **文件**：`verl/workers/engine/fsdp/transformer_impl.py` 等
- **改动**：merged LoRA 权重在 `merged_lora_context` 内物化再同步；配套
  `patch_verl_merged_lora.py` 幂等应用
- **原因**：`lora.merge=True` 时 rollout 同步的是基座权重（不带 adapter），
  梯度更新从未生效（verl#7014 上游 bug）
- **影响**：LoRA 微调质量修复，baseline / spec / 黑盒 / 双机全部依赖
- **记录**：verl commit `c2049af`（backport）

### 3. 权重同步 IPC 对 CPU 大张量崩溃（2026-08-05 实测）

- **文件**：`verl/workers/rollout/vllm_rollout/bucketed_weight_transfer.py`
- **改动**：`_direct_send_large_weight` 发送前把 CPU 张量 `.to(cuda)` 再
  `reduce_tensor`（`patch_verl_ipc_cpu.py` 幂等应用）
- **原因**：LoRA 首次基座权重同步把权重搬到 CPU 收集，embedding ~1.09GB 超过
  bucket 时走 IPC；CPU 张量句柄参数不足，接收端 `rebuild_ipc` 的
  `list_args[6]` IndexError → worker 崩溃
- **影响**：多机权重同步稳定性；双机所有实验前置修复

### 4. StrEnum 兼容 Python 3.10

- **文件**：`verl/utils/tokenizer/continuous_token_wiring.py`（及相关文件）
- **改动**：`from enum import StrEnum` → try/except 回退 `strenum`（
  `fix_strenum_ucloud.sh` 全库扫描幂等替换 + pip 装 StrEnum）
- **原因**：verl 上游要求 Python 3.11+（StrEnum 3.11 才进 stdlib），
  服务器 conda 环境为 3.10

### 5. debug 指标缺键容错

- **文件**：`verl/utils/debug/metrics.py`
- **改动**：`calculate_debug_metrics` 在 `rollout_log_probs` 缺键时跳过并告警
  （返回 NaN 占位），不再 KeyError 崩训练
- **原因**：多轮 agentic 批次中存在重试/失败的 episode（无 rollout logprobs）
  时整批缺该键

### 6. num_turns NestedTensor 兼容（双机阶段新增）

- **文件**：`verl/trainer/ppo/v1/trainer_base.py` `_compute_metrics`
- **改动**：`num_turns` 为 NestedTensor（ragged）时先
  `to_padded_tensor(0).reshape(-1)` 再取，普通张量走原路径
- **原因**：agent 框架轨迹的 num_turns 经 TransferQueue MooncakeStore 重组后
  可能为 NestedTensor，`.tolist()` 抛 RuntimeError（step 完成后崩训练）
- **影响**：仅每步一次的指标计算；train3 验证 step 完成、reward 1.0

### 7. logprobs 防御式提取（双机阶段新增，两台机器均应用）

- **文件**：`verl/workers/rollout/vllm_rollout/vllm_async_server.py`
- **改动**：logprobs 提取改为**按 token_ids 遍历**（token_ids 为准），
  逐位兼容 dict / list-of-Logprob 结构，错位时缺失位回退 0.0 并跳过多余位
- **原因**：vLLM 0.11.1 spec-decode + chunked prefill 返回的 logprobs 列表与
  token_ids 长度错位（PR #29216 同族 bug，0.14 才移除 spec-decode 对 logprobs
  的限制）；原 `logprobs[token_ids[i]]` 两种方向都会 IndexError → 整请求 500
- **影响**：引擎不再因 logprobs 结构崩请求；防御检查每 token 微秒级；
  修复后双机验证 0 API 错误

## 二、uni_agent Gateway 层

### 8. hermes 工具调用解析容错（v0.31.8）

- **文件**：`uni_agent/gateway/session/codec.py`
- **改动**：`extract_tool_calls` 失败 → JSON repair 重试 → 仍失败则注入合成

- **原因**：模型工具调用 JSON 偶发格式瑕疵，原实现静默返回无工具消息 →

## 三、TransferQueue / Mooncake 层（双机阶段）

### 12. clear_data KV 模式跳过（两台机器均应用）

- **文件**：`transfer_queue/storage/managers/base.py`（site-packages）
- **改动**：`clear_data` 在 `BatchMeta.field_names` 为空（KV 模式）时跳过并
  告警，不再 raise
- **原因**：verl v1 replay_buffer 的 `kv_clear` 只传 keys/global_indexes；
  MooncakeStore（KV 后端）的 clear_data 要求 field_names → 验证阶段崩溃；
  verl 每样本 uid 唯一，残留条目不可达、无脏读

### 13. `MC_STORE_MEMCPY=0`（mooncake 禁用 GPU 拷贝引擎）

- **原因**：mooncake 默认把 GPU 当拷贝引擎（cudaMemcpy），与同卡 vLLM 内存
  管理冲突（colocate 场景 CUDA illegal memory access）；TCP 无 RDMA 下
  纯内存拷贝足够，实测 D/E 无性能差异（48.1 vs 48.2s）
- **注入方式**：Ray raylet 启动环境（worker 继承），双机

### 14. Mooncake 部署修正

- **mooncake_master 预启动**：auto_init 依赖 PATH（Ray worker 不继承 driver
  PATH）且缺 `libcudart.so.12` → 手动预启动（LD_LIBRARY_PATH 指向 conda
  cuda_runtime）+ 脚本 `MOONCAKE_AUTO_INIT` 可配置（False）
- **node2 补装**：`mooncake-transfer-engine==0.3.12.post1`（与 node1 同版本）
- **local_hostname=""**：默认 localhost 会让跨节点客户端注册成 127.0.0.1；
  置空串按 Ray 节点 IP 自动注册

## 五、性能影响评估

- 所有补丁均为**正确性/稳定性修复**，不进入训练热路径：
  - 指标类（6、8、11）每步/每会话一次，可忽略
  - logprobs 防御提取（7）每 token 微秒级 `isinstance` 检查，相对生成耗时
    可忽略，且**防止请求失败**（保住吞吐而非拖慢）
  - 权重同步类（2、3）为多机/投机前置修复，不改变单步开销
  - 环境类（4、13、14、15）为部署修正，实测双机 D/E 无性能差异
- 双机对照实测：sync 79.4s/步 → separate_async 48.1s/步（-39%），
  Mooncake vs SimpleStorage 48.2 vs 48.1s（无差异），全部修复后 0 崩溃
