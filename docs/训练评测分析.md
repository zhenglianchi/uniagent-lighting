# HumanEvalFix GRPO 训练与评测分析

## 1. 概述

以 HumanEvalFix（bigcode/humanevalpack Python 修复子集，161 条）为基准，基于
Qwen/Qwen3-8B 完成三条 GRPO（LoRA）训练路径，全部为平台化训推链路产出：

| 路径 | Harness | 训练步数 | 评测通过率 |
|---|---|---|---|
| 白盒 baseline | mini-swe-agent | 26 步（5 epoch + 1） | **83.2%** |
| 白盒 spec | mini-swe-agent + EAGLE-3 | 25 步（5 epoch） | **82.61%** |
| 黑盒 | Claude Code | 25 步（5 epoch） | **80.75%** |

基座评测 76.4%（123/161），三条路径分别提升 +6.8pp / +6.2pp / +4.35pp。

## 2. 训练配置

统一口径：train161 / batch32 / mini16 / micro4 / n=4 / 并发 64 / max_num_seqs
128 / vllm util 0.8 / 5 epoch / LoRA rank=32 / AdamW(fp32) / 梯度检查点 /
`resume_mode=auto`。

### 2.1 白盒 baseline（2026-08-08 ~ 09）

26 步，总 token 1105.6 万，总时长 15.3h，平均单步 35.4min，平均吞吐 200.2
tok/s。逐步 reward mean：step1 0.289 → step5 0.500 → step26 0.659；训练使
"越修越快"——轮数从 epoch1 17.6 降至 epoch5 9.0（-49%），单步时长 -34%。

### 2.2 白盒 spec（2026-08-09 ~ 10）

25 步，EAGLE-3 投机解码 + `lora.merge=True`。生成吞吐 +41.7%（199.2 → 282.4
tok/s），单 token 延迟 -39.5%（6.70 → 4.05ms），每步生成耗时 -25.7%，提速全程
稳定（step1-5 +42% / 6-15 +47% / 16-25 +36%）。修复期间发现的 verl#7014
merge 权重物化 bug（训练梯度未作用到 rollout）后重跑。

### 2.3 黑盒（2026-08-12 ~ 13）

25 步（step 1-5 首跑 + 换服务器续训至 25），Claude Code 2.1.153（沙箱内编排，
max_turns 60）。奖励曲线 0.43 ~ 0.74 波动，累计通过率约 60%；每步 65-110
分钟（白盒 30-35 分钟），gen 占 75%+。

## 3. 评测方法

n=1 / temperature 0.8 / 161 条 / 并发 24，vLLM 参数与训练一致
（`--enable-auto-tool-choice --tool-call-parser hermes --enable-prefix-caching`）。
评估前先以 3 条小样本验证轨迹与真实 pytest 结果，再全量评估；reward 为
`test_solution.py::test_all` 的真实 pytest 通过率。

## 4. 行为对比（黑盒 vs 白盒）

| 指标 | 白盒 baseline | 黑盒 |
|---|---|---|
| 单步时长 | 35 分钟 | 65-110 分钟 |
| 平均轮数 | 11.4（训练后降到 8-10） | 16-28（无下降） |
| 响应长度 | 1665 tokens | 3158 tokens |
| 吞吐 | 199 tok/s | 130 tok/s |
| 训练 reward mean | 0.589 | ~0.60 |
| step1 起点 | 0.29 | 0.57 |
| 最终评测 | 83.2% | 80.75% |

黑盒（Claude Code 编排）起点通过率显著更高，但轮数/时长约白盒 2 倍，吞吐低
35%（长上下文 prefill 重复 + prefix cache 命中不足）；白盒训练表现出收敛特征
（轮数 -49%），黑盒无此趋势。

## 5. 性能优化与源码排障

- **EAGLE-3 投机解码**：吞吐 +41.7%、延迟 -39.5%，训练质量无损
- **LoRA 引擎热插**：每步权重同步 2.5s vs 全量 15GB
- **Gateway 解析容错**：5.3% 解析错误率（38% 会话受影响）修复为 0 会话失败
- **上游 bug**：verl#7014（merge 梯度未生效）、vllm#30059（EAGLE-3 logprobs
  全丢）、gateway 解析（JSON repair + 合成重试）

## 6. 结论

1. 三条训练路径均显著提升 HumanEvalFix 通过率（基座 76.4% → 80.75~83.2%）
2. 投机解码在训练链路中无副作用，吞吐收益 +41.7%
3. 黑盒（Claude Code）编排初始能力强，但训练效率低（轮数/时长 2 倍），
   作为平台化双 harness 的对比样本
4. 全部结果由平台化训推链路产出，可加载/继续训练

## 7. 双机全异步 + Mooncake 对照实验（2026-08-14）

### 7.1 背景与目标

双机各 1×RTX 4090 48G（内网互连，NCCL 实测 1.81GB/s），验证在投机解码基础上
"全异步 + TQ Mooncake" 的收益与稳定性，为正式双机训练定架构。所有实验保持
baseline 口径（并发 64 / max_num_seqs 128 / util 0.8），小样本每步 2 样本 × 2
响应（token 量 4704/步），跑 3 步取均值。

### 7.2 实验矩阵（vLLM 0.11.1 + verl 0.9.0.dev v1 + TransferQueue 0.1.9）

| 实验 | 架构 | TQ 后端 | 结果 | 每步耗时均值 | 吞吐 |
|---|---|---|---|---|---|
| A | sync（dp=2 双引擎） | SimpleStorage | ✅ 跑两遍全干净 | **79.4s**（重跑 74.0s） | 25-36 tok/s |
| B | colocate_async | SimpleStorage | ⚠️ 首跑 3/3 干净，重跑 step1 崩溃 | 77.5s | ~33 tok/s |
| C | colocate_async | MooncakeStore | ❌ 2/2 崩溃（step1 生成 CUDA illegal memory access） | — | — |
| D | **separate_async**（trainer 1 卡 + 独立引擎 1 卡） | SimpleStorage | ✅ 3/3 | **48.1s** | 79-155 tok/s |
| E | **separate_async** | MooncakeStore | ✅ 3/3 | **48.2s** | 77-167 tok/s |

### 7.3 结论

1. **separate_async 比 sync 快约 39%**（79.4s → 48.1s/步）：trainer 与独立
   rollout 引擎分卡并行，生成完全重叠，update_actor 仅 3-6s；当前每步瓶颈为
   nccl 权重同步 ~27s（batch=2 时 parameter_sync_step=1，每步全量同步；
   正式训练 batch=32/mini=16/pss=2 可摊薄）
2. **colocate_async 在 vLLM 0.11.1 上不稳定**（CUDA illegal memory access，
   多轮生成 resume 时 sleep/wake 竞态；B 重跑亦崩，与 Mooncake 无关），
   不作为正式架构
3. **Mooncake 在双机 TCP（无 RDMA）下与 SimpleStorage 无差异**（48.2 vs
   48.1s），符合小数据量预期；但架构可稳定跑通，后续加 RDMA / 大 batch 再评估
4. **投机解码在 separate_async 下可恢复**：独立引擎单节点 dp=1，避开
   EAGLE-3 + dp>1 的 vLLM 死锁（实验 A 首炸根因），正式 E 训练已开 EAGLE-3

### 7.4 排障记录（双机 + Mooncake）

- **EAGLE-3 + dp>1 死锁**：vLLM 0.11.1 动态投机与 data_parallel_size>1 不兼容
  （EngineCore shm_broadcast TimeoutError）；跨节点 tp=2 又因 verl v1 每节点
  单引擎设计 + 硬编码 mp executor 不支持 → 双机投机只能在独立引擎 dp=1 形态
- **mooncake_master 启动**：auto_init 依赖 PATH（Ray worker 不继承 driver
  PATH）且缺 libcudart.so.12 → 手动预启动（LD_LIBRARY_PATH 指向 conda
  cuda_runtime）+ 脚本 `MOONCAKE_AUTO_INIT` 可配置
- **node2 缺 mooncake-transfer-engine**：补装 0.3.12.post1（与 node1 同版本）
- **MooncakeStore local_hostname**：默认 localhost 会导致跨节点客户端注册为
  127.0.0.1，需置空串按 Ray 节点 IP 自动注册
- **GPU memcpy 冲突**：mooncake 默认把 GPU 当拷贝引擎（cudaMemcpy），与同卡
  vLLM 冲突；`MC_STORE_MEMCPY=0` 禁用（Ray raylet 环境注入）
- **TQ 0.1.9 clear_data 不兼容**：MooncakeStore（KV 后端）clear_data 要求
  BatchMeta 带 field_names，verl v1 replay_buffer 的 kv_clear 只传 keys →
  补丁 base.py 空 field_names 时跳过并告警（verl uid 唯一，无脏读风险）
- **verl _compute_metrics NestedTensor**：agent 框架轨迹 num_turns 在
  MooncakeStore 重组后可能为 NestedTensor，`.tolist()` 崩溃 → 补丁兼容
  to_padded_tensor 路径

### 7.5 正式双机训练（E 架构）

`scripts/run_grpo_dual_async_mooncake_ucloud.sh`：黑盒（Claude Code）HumanEvalFix
161 条、batch 32 / mini 16 / micro 4 / parameter_sync_step=2、并发 64 /
max_num_seqs 128 / util 0.8、n=4、多轮 60 轮、EAGLE-3 投机 + MooncakeStore +
separate_async 全开；trainer 占 node1、独立 rollout 引擎占 node2。小样本
（train3）全链路验证通过后启动（step 约 6 分钟/批，reward 全 1.0，指标正常），
训练完成后自动接全量评估。验证阶段另确认两个要点：
- **logprobs 防御补丁**：vLLM 0.11.1 spec-decode + chunked prefill 偶发返回
  错位 logprobs（PR #29216 同族），standalone 引擎曾 3/12 会话段报 500；verl
  提取逻辑已改防御式（dict/list 兼容、缺失回退 0.0），不再崩引擎
- **checkpoint 跨节点落盘**：separate_async 的 FSDP worker 在 node2，actor
  权重存 node2 本地 `/home/ubuntu/swe-rl/checkpoints/.../global_step_N/actor/`，
  trainer 侧 data.pt/tracker 在 node1；配套 `run_dual_formal_chain.sh` 负责
  训练后拉回 actor 目录 → LoRA 合并 → vLLM 评估（n=1、temp 0.8、161 条、并发 24）

### 7.6 Mooncake num_turns 13B 排查与离线验证（2026-08-15）

**现象**：双机真实训练（128 会话，batch 32 × n 4）偶发
`Buffer too small for key 'X@num_turns': required=13, available=8`
（`real_client.cpp:4664`），重试 3 次后训练崩溃；坏 key 每次运行随机
（首轮 0/3/4 等，二轮 32 等）。从运行中 store dump 确认该 key 存了 13 字节。

**根因定位（写读类型不一致，非内存损坏）**：
- 13 字节内容 `01000000 0c000000 01000000 00` 是 **TQ msgpack 打包的小整数**
  （4B 条目数 + 8B 索引 + 1B 载荷，`serial_utils.encode(0)` 逐字节复现）——
  即 `num_turns` 被**非张量字节路径**写入（Python int → 13B），而训练端按
  int64 张量（8B）读取 → 大小不匹配。
- 框架（`uni_agent.framework.framework._trajectory_to_tq_field_and_tag`）写
  `num_turns` 恒为 `torch.tensor(int(...), dtype=torch.long)`（8B）；TQ
  `_batch_upsert_with_retry` / `merge_contiguous_memory` / `allocate_empty_tensors`
  的 key/值/大小顺序一致、size 原样透传，无逻辑错误；C++ 端
  `batch_upsert_from` → `BatchUpsert` 用 per-op futures，顺序保持。
- **官方社区**：无完全匹配的 open issue。最接近的三个 C++ bug 均已修复且包含在
  已装的 `mooncake-transfer-engine 0.3.12.post1`：
  - PR #1704（TENT batch transfer 跨独立注册 buffer 边界错误合并，v0.3.11 起）
  - Issue #2086 + PR #2850（TCP WRITE 无完成确认，大描述符撕裂写，engine.so 内
    已确认含 `MC_TCP_PROTO` / `tcp_proto_version`）
  - Issue #2477 + PR #2714（TENT SegmentManager::local_desc_ 数据竞争）
- 单机场景无法复现：合成（大字段 + 8 writer 并发 + index 复用，4 轮 1024 keys）
  与离线真实轨迹（508 条轨迹 → 2048 keys）均 0 异常 → 13B 依赖双机跨节点特定
  并发条件（或当时环境的偶发异常写入路径）。

**离线真实轨迹验证（2026-08-15，node1 单机）**：
- 加载真实黑盒 / 平台化训练轨迹（`trajectory.json` + `trajectory.npz`，共 508 条），
  用框架同款字段构造（prompts/responses/input_ids/position_ids/rm_scores/
  num_turns/session_id/global_steps/uid/extra_info...），TQ `kv_batch_put` 写入
  MooncakeStore，8 writer 并发 + 4 轮 + `kv_clear` 释放/复用 global index，
  共 **2048 keys**。
- TQ 写路径日志（`TQ_DEBUG_WRITE=1`）：全部 `X@num_turns` 均为 Tensor 路径；
  读回值正确（真实 num_turns）。
- 直接连 mooncake store dump：每轮 512 个 `X@num_turns` 键 `get_size` 全为 8，
  **0 异常**。
- 结论：**Mooncake 写入链路单机/离线正确**；可作为"Mooncake 写入正确"的验证依据。

**防御措施（已落地）**：
- 读端 `_get_with_padded_buffers` 兜底（防崩，但救不回坏值）。
- 写端新增断言：TQ `mooncake_client._batch_upsert_with_retry` 对 `@num_turns`
  键 size != 8 立即 `logger.error`（双机正式训练再现时可精确定位写来源）；
  node2 待重启后同步该补丁。
- 排查期环境问题修复记录：GatewayActor 不继承脚本 `GATEWAY_PORT`（随机端口导致
  claude-code 连不上，需在 `ray start` 前 export）；腾讯沙箱 CPU 配额被残留
  RUNNING 实例占满（`tencent_stop_all_instances.py` 已确认实例字段为
  `InstanceSet`）；node1 sshd 默认 `MaxStartups 10` 对高并发隧道限流。

### 7.7 单机在线验证 + 两个新 bug 修复（2026-08-15）

**背景**：13B 离线验证通过后，在 node1 单机（1×4090 48G）跑 48 会话在线验证
（`run_grpo_single_mooncake_ucloud.sh`，train12b × n4，util 0.6 / max_num_seqs 64 /
并发 24，vLLM 0.11.1 + EAGLE-3 + MooncakeStore），连续暴露两个独立问题。

**问题一：vLLM EAGLE-3 rejection sampler CUDA illegal memory access（与 Mooncake
无关，上游竞态）**

- 现象：rollout 48/48 全部成功（`generate_sequences summary`）后，vLLM EngineCore
  在 `rejection_sampler._get_logprobs_tensors` 报
  `CUDA error: an illegal memory access`，trainer 卡死。
- 关键日志：崩溃前 1 秒 `Failed to reset prefix cache because some blocks (939) are
  not freed yet` → reset 失败后引擎继续采样，访问已失效 KV block → 越界。
- 对比：历史白盒 run（单机 spec 25 步、双机 async）全部 **0 次** illegal memory /
  reset 失败；`grpo_humanevalfix_spec.log` 与双机日志均已核实。
- 根因：vLLM 0.11.1（2025-11-17 老版本）EAGLE-3 + async 调度 + `free_cache_engine`
  （reset prefix cache）组合下 lookahead block 释放不干净；上游 2026 年中已有多处
  修复（async in-flight frame #47900、rejection sampler int32 overflow #48055、
  NaN tl.argmax #50183），0.11.1 均不包含。
- 触发条件差异：util 0.6 → KV cache 更小，长上下文多轮会话更易踩中；**恢复
  baseline/spec 同口径 util 0.8 后 24 会话全流程 0 崩溃**。

**问题二：Mooncake INVALID_PARAMS 空 slice（framework 空响应轨迹，已修复）**

- 现象：24 会话验证中 1 个 session 的 TQ 写入失败
  （`18@loss_mask / response_mask / responses / rm_scores`），master 报
  `slice_length=0, error=invalid_params`，重试 3 次后整个 session 失败。
- 根因：`max_trajectory_length` 截断产生的**空响应轨迹**（`response_ids (0,)`、
  `materialization_reason=max_trajectory_length`）被 `_write_session_trajectories_to_tq`
  照常写入 TQ；responses/rm_scores/loss_mask/response_mask 4 个字段均为 0 字节 slice，
  Mooncake master 拒绝 0 长度写入。
- 修复：`uni_agent/framework/framework.py` 写入时跳过空响应轨迹（并重编号 index 保证
  key 连续），补丁 `patches/uni_agent_skip_empty_response_trajectory.patch`；
  TQ `mooncake_client` 增加 0 字节 slice 告警（`patches/tq_mooncake_zero_slice_warn.patch`）。

**修复后 24 会话在线验证（util 0.8）✅**：

- rollout `num_success_sessions=24, num_failed_sessions=0`；空轨迹跳过告警 1 条生效；
  全程 0 `INVALID_PARAMS`、0 `Buffer too small`、0 vLLM 崩溃。
- GRPO step 1 正常完成（202348 tokens），`global_step_1` checkpoint 保存，进程正常退出。
- 结论：**单机 Mooncake + EAGLE-3 + util 0.8 全链路稳定**；vLLM 崩溃为 util 0.6
  触发条件，正式训练保持 util 0.8 即可规避。

### 7.8 为什么历史白盒 run 不出现这些问题（差异归因）

**结论先行：之前白盒能稳定跑通，是因为它根本没有走今天出问题的两条链路；
今天的两个问题都是"首次启用新链路 + 新配置"后暴露的，与白盒/黑盒模型无关。**

**1）TQ/Mooncake 类问题（num_turns 13B、Buffer too small、INVALID_PARAMS 空
slice）——之前白盒 `transfer_queue.enable=False`，根本没用 TQ KV + Mooncake：**

- 白盒 baseline（8-8~9）与 spec（8-9~10）训练日志
  `grpo_humanevalfix_full.log` / `grpo_humanevalfix_spec.log` 的 trainer 配置段均
  为 `'transfer_queue': ... 'enable': False` → verl 走默认数据平面，不经过 TQ KV
  写入，因此不会出现 `@num_turns` 13B 或空 slice 被 Mooncake 拒绝的问题。
- 双机 async（8-14）才第一次 `transfer_queue.enable=True` +
  `storage_backend=MooncakeStore`（日志已核实），且只跑了少量验证步，样本少，
  13B（偶发）与空响应轨迹（需长会话触发 `max_trajectory_length`）均未全量暴露。
- 结论：这些是 **TQ/Mooncake KV 链路本身的 bug**，不是白盒训练引入的；白盒正式
  训练复跑（enable=False 路径）不受任何影响。

**2）vLLM EAGLE-3 illegal memory——之前白盒 spec run 与本次唯一配置差异是
`util`：**

- spec run（25 步，util 0.8 / max_num_seqs 128 / 并发 64）：每次
  `reset_prefix_cache` 全部成功（日志 0 次 `Failed to reset prefix cache`），
  KV 空间充足，从不触发 EAGLE-3 lookahead block 释放竞态。
- 本次单机验证（util 0.6 / 64 / 24）：KV cache 更小，长上下文多轮会话触发
  reset 时 939 blocks 未释放 → 后续采样访问失效 KV → illegal memory。
- 结论：崩溃是 **util 配置触发的 vLLM 上游竞态**（0.11.1 老版本），与白盒/黑盒、
  与 Mooncake 均无关；恢复 util 0.8 即回到 spec run 的稳定区间。

### 7.9 空轨迹与 num_turns 13B 的完整产生机制（2026-08-15 深挖定稿）

#### A. 空响应轨迹（Mooncake INVALID_PARAMS）的完整产生机制

**设计背景**：训练配置 `max_prompt_length + max_response_length` 决定 Gateway 的
单条轨迹容量上限（spec run 为 4096+4096=8192；单机验证为 8192+8192=16384）。
agent 会话最多 60 轮、上下文会持续累积，Gateway 必须防止单条轨迹无限膨胀。

**链分片设计**：Gateway（`uni_agent/gateway/session/session.py`）把会话生成内容
放在"链"（chain）里，每轮输出累积进该链的 `response_ids`；链总长
（`prompt_ids + response_ids`）达到容量上限时，把链"物化冻结"成一条轨迹，然后开
新链继续生成——这样单条轨迹永不超限，agent 也能跑完 60 轮。

**触发链条（逐行）**：

1. `_prepare_generation_inputs`：续链请求时计算
   `current_trajectory_length = len(prompt_ids) + len(response_ids)`；
   若 `current + len(incremental_ids) >= capacity` → `capacity_exhausted=True`
   （本轮增量不追加进 buffer）。
2. `run_generation`：`capacity_exhausted` 时不调用模型，返回
   `{"role": "assistant", "content": ""}` + `finish_reason="length"`；
   若选中了已有链（`chain_id` 非空）→ `_close_length_exhausted_chain` 把该链
   物化进 `materialized_chains`，标记 `materialization_reason=max_trajectory_length`。
3. **agent 侧不终止**：mini-swe-agent 主循环（`agents/default.py`）只认
   `step_limit`（60 轮）/ `cost_limit` / 显式 `exit` 消息三种终止；
   `finish_reason="length"` 对它是"空回复，无工具调用"，继续下一轮。
4. **开新链**：物化后 `active_chains` 为空，agent 下一轮请求
   `_select_chain` 返回 None → 创建新链
   `TrajectoryBuffer(prompt_ids=完整历史重编码)`，`response_ids` 从 0 开始。
5. **新链第一轮必空**：新链 `prompt_ids` = 全部历史（spec 例 8168、单机例
   16376），剩余容量仅 24/8 tokens；加上本轮增量（工具结果，通常数百 token）
   再次触发 `capacity_exhausted` → 模型仍不生成 → 新链被物化为**空响应轨迹**
   （`response_ids (0,)`）。

**真实实例（spec run sample-5-rollout-2，容量 8192）**：

```
链 A：第 1 轮 prompt=1248 → 逐轮累积 response → 第 25 轮 1248+6791=8039
第 26 轮请求（历史已 8168 tokens）→ 8039+增量 ≥ 8192 → 耗尽
  → 物化链 A = 轨迹[0]：25 轮、prompt 1248、response 6791（✅ 有效完整）
agent 继续第 26 轮 → 新链 B：prompt=8168、response 空 → 又耗尽
  → 物化链 B = 轨迹[1]：26 轮、prompt 8168、response 0（❌ 空占位）
```

**评价**：链分片本身合理（支持超长会话续跑），缺陷在于"新链几乎无生成空间却仍
被创建并物化"——Gateway 乐观假设"新链还有少量余量能再产出几步"，实际 agent 每
开新链第一轮就耗尽，频繁产出空轨迹。

**对训练的影响**：
- 有效轨迹（轨迹[0]）完整保留，不受影响；
- 空轨迹无训练价值（`loss_mask` 全 0、`rm_scores` 空，不贡献梯度）；
- **SimpleStorage 后端**：空轨迹能写入（容忍 0 字节/任意大小），只浪费一个
  batch slot，基本无害——这是之前白盒 45 个空轨迹却不崩的原因；
- **Mooncake 后端**：空轨迹 4 个字段（responses/rm_scores/loss_mask/
  response_mask）为 0 字节 slice，master 以 `INVALID_PARAMS` 拒绝 → **整个
  session 的 TQ 写入失败**（连有效轨迹也丢）→ batch 不齐 → 触发 padding
  （与 B 节 13B 联动）。

**修复**：framework `_write_session_trajectories_to_tq` 跳过
`len(response_ids)==0` 的轨迹并重编号 index（补丁 #20）。

#### B. num_turns 13B（Buffer too small）的完整产生机制

**现象**：双机真实训练偶发
`Buffer too small for key 'X@num_turns': required=13, available=8`，坏 key 随机。

**13B 内容解码**：`01000000 0c000000 01000000 00` = TQ msgpack 打包的小整数 0
（4B 条目数 + 8B 索引 + 1B 载荷），用 `serial_utils.encode(0)` 可逐字节复现。

**写入端（谁写的）**：**verl 训练端 TaskRunnerV1**，不是 agent 框架：

1. `trainer_base._balance_batch`（v1/trainer_base.py:1244）发现 batch 数量不能被
   `batch_multiple` 整除（dp 与 mini-batch 的 LCM）→ 调用
   `upsample_batch_to_divisible_size` 补 padding 行；
2. `padding_utils.construct_minimal_padding_template`（padding_utils.py:109）
   构造合成补行，其中 `num_turns=0` 是 **Python int**（其余字段多为 tensor）；
3. `tq.kv_batch_put` 把 padding 行**写回 TQ store**。

**编码分流（为什么是 13B）**：TQ 写路径按值类型分流——`torch.Tensor` 走张量
路径（int64 8B）；Python int 走 msgpack 字节路径（打包成 13B）。agent 框架写的
`num_turns` 恒为 `torch.tensor(int(...), dtype=torch.long)`（8B 正确），只有 verl
padding 行偷懒用了裸 int。

**读端**：训练进程按 int64 8B 分配 buffer 读 `@num_turns`，store 里是 13B →
`required=13, available=8` → Buffer too small（Mooncake 客户端报错后重试）。

**责任方结论**：verl 训练端 `padding_utils.py` 类型不一致 bug；agent 框架无责
（恒写 8B tensor）；TQ/Mooncake 忠实传输（非张量走 msgpack 是其设计行为）。

**为什么之前不出现**：
- spec/baseline 的 batch 完整整除（128÷32），日志 **0 次** `Upsampled batch`
  （padding 从未触发）；
- 即便触发，SimpleStorage 读端不按固定 8B 强校验（或按实际 size 还原），不会
  炸；8-15 单机 48 会话 batch 不齐首次触发 padding + Mooncake 读端 8B 校验
  → 176 条 Buffer too small。

**修复**：`padding_utils.py:109` `num_turns=0` →
`num_turns=torch.tensor(0, dtype=torch.long)`（补丁 #22）；48 会话验证
Buffer too small 176→0、size!=8 断言 88→0。

#### C. 两个 bug 的关系与统一归因

- **共同点**：都发生在 TQ KV 写路径上，都是"占位/空数据"的编码大小与正常数据
  不一致：空轨迹是 0 字节 slice（空 tensor），padding 行是 Python int 的 13B
  （msgpack）。两者独立触发、独立修复。
- **可联动**：空轨迹写入失败 → session 失败 → batch 样本不足 → 触发 padding →
  13B 出现。
- **为何之前白盒不崩**：之前的后端是 **SimpleStorage**，容忍空数据与任意大小；
  Mooncake 严格要求（master 拒绝 0 字节、读端固定 8B）。空轨迹之前就有
  （baseline 37 个 / spec 45 个 `response_tokens=0`，截断轨迹 420/622 个），
  只是换到 Mooncake 才被引爆。
